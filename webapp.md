# ТЗ: веб-интерфейс к боту учёта бюджета

Продолжение `plan.md`. Документ — исполняемая спецификация, реализовывать
строго по фазам, снизу вверх. Не забегать вперёд, не добавлять
функциональность, которой здесь нет.

Зачем: бот хорош для записи на ходу, но плох для разбора. Опечатку в сумме в
нём не исправить вообще, а увидеть картину за месяц можно только четырьмя
блоками текста. Веб закрывает ровно эти две дыры — правки и графики.

---

## 0. Правила работы

Всё из `plan.md` §0 остаётся в силе: Go, `pgx/v5` + голый SQL, никаких ORM,
`log/slog`, все тексты на русском, после каждой фазы зелёная сборка и тесты,
затем коммит.

Что меняется относительно `plan.md`:

- **§14 отменяется в части «Веб-сервер, HTTP-эндпоинты»** — он теперь есть.
  Остальные запреты §14 в силе: ни долгов, ни мультивалютности, ни тегов,
  ни повторяющихся платежей.
- **Появляется второй язык.** Фронт — React 18 + Vite + TypeScript. Сборка
  фронта укладывается в `embed.FS`, бинарь остаётся самодостаточным: на
  проде по-прежнему один файл и одна база.

Что не меняется и меняться не должно:

- Бот и веб — **один бинарь, одна база, один systemd-юнит**. Никаких
  микросервисов, никакого отдельного API-процесса.
- **Веб не обращается к LLM ни при каких условиях.** Разбор текста — дело
  бота. Веб только читает и правит уже записанное, поэтому токенов не тратит
  и в защитный лимит `plan.md` §7 не вмешивается.
- Правила предметной области одни на оба интерфейса. Менять и удалять чужие
  записи нельзя (`plan.md` §9), ручная правка уезжает в `word_map` с
  `source='manual'` (`plan.md` §8), удаление только мягкое (`plan.md` §3).
  Если правило продублировано в вебе — это ошибка, оно должно жить в одном
  месте и вызываться из обоих.

## 1. Аутентификация

Самая опасная часть: сервис торчит в интернет, а за ним полугодовая история
личных трат.

Паролей и регистрации нет — `plan.md` §14 закрывает этот вопрос, и открывать
его заново незачем. Доверенный канал уже есть: бот. Через него и входим.

### Вход по одноразовой ссылке

1. Пользователь пишет боту `/вход` (латиницей `/login`).
2. Бот проверяет whitelist, генерирует токен — 32 байта из `crypto/rand`, —
   пишет в `login_tokens` его **SHA-256, а не сам токен**, и отвечает
   ссылкой `https://<host>/auth?token=<токен>`.
3. Токен живёт 5 минут и срабатывает один раз. Второй переход по той же
   ссылке — отказ.
4. `/auth` проверяет токен, помечает использованным, заводит сессию, ставит
   cookie и редиректит на `/`.

Ссылка приходит в личку тому, кто её запросил, и живёт минуты — этого
достаточно. Отдельная ценность: отозвать доступ можно, убрав id из
`ALLOWED_USER_IDS`, и все его сессии умрут при следующем же запросе.

### Сессия

- Токен сессии — те же 32 случайных байта, в базе только SHA-256.
- Cookie: `HttpOnly`, `Secure`, `SameSite=Lax`, срок 30 дней. Без TLS флаг
  `Secure` ставить нельзя — браузер просто выбросит cookie, — поэтому режим
  без него включается явно: `WEB_INSECURE_COOKIES=1`.

  **Что это значит.** По HTTP и ссылка входа, и cookie сессии едут открытым
  текстом. Кто угодно между телефоном и сервером — чужой Wi-Fi, провайдер —
  видит их и может зайти под тобой, то есть прочитать и переписать всю
  историю трат. Пока сервис не торчит в интернет и открывается из домашней
  сети, это терпимо. Как только адрес станет публичным, TLS обязателен —
  Caddy с доменом делает это двумя строками, см. §3.
- На **каждом** запросе: cookie → сессия → `user_id` → проверка
  `ALLOWED_USER_IDS`. Whitelist проверяется всегда, а не только при входе.
- `last_seen_at` обновляется не чаще раза в час: писать в базу на каждый
  запрос ради статистики незачем.
- Выход — `DELETE /api/session`. «Выйти со всех устройств» —
  `DELETE /api/session?all=1`.

**Никакого JWT.** Подписанный токен нельзя отозвать до истечения срока, а
таблица сессий даёт кнопку «выйти отовсюду» ценой одной миграции.

### Защита от перебора

- `/auth` — не больше 10 попыток в минуту с одного адреса, дальше 429.
- Сравнение хэшей — `subtle.ConstantTimeCompare`.
- В логи токены не пишутся никогда, даже частично.

## 2. Схема БД

`migrations/0004_web.sql`:

```sql
-- +goose Up
create table login_tokens (
    token_hash  bytea primary key,
    user_id     bigint not null references users(id),
    created_at  timestamptz not null default now(),
    expires_at  timestamptz not null,
    used_at     timestamptz
);

create table web_sessions (
    token_hash    bytea primary key,
    user_id       bigint not null references users(id),
    created_at    timestamptz not null default now(),
    last_seen_at  timestamptz not null default now(),
    expires_at    timestamptz not null,
    user_agent    text
);

create index web_sessions_user_idx on web_sessions (user_id);

-- Правка задним числом должна быть видна хотя бы по метке времени.
alter table transactions add column updated_at timestamptz;

-- +goose Down
alter table transactions drop column updated_at;
drop table web_sessions;
drop table login_tokens;
```

Протухшие строки обеих таблиц чистятся при каждом входе — отдельного крона
на две записи в неделю заводить не нужно.

## 3. Транспорт и деплой

- Сервер слушает `WEB_ADDR`, по умолчанию `127.0.0.1:8081` — порт свободен,
  соседние 3000-3005 и 8000 заняты чужими контейнерами.
- **Первая итерация — по HTTP, без прокси и TLS**: `WEB_ADDR=0.0.0.0:8081`,
  `WEB_BASE_URL=http://<ip-машины>:8081`, `WEB_INSECURE_COOKIES=1`.
  Открывается из локальной сети. Ограничения этого режима — в §1.
- Дальше — реверс-прокси с TLS, код при этом не меняется: меняются две
  переменные окружения.
- `WEB_BASE_URL` — публичный адрес, из него бот собирает ссылку входа.
  Пустой `WEB_BASE_URL` означает «веба нет»: сервер не поднимается, `/вход`
  отвечает, что интерфейс не настроен. Бот при этом работает как работал.
- Если `WEB_BASE_URL` задан, а порт занят — падаем на старте. Сервис,
  который наполовину работает и молчит об этом, хуже упавшего.

Вариант с Caddy (домен уже смотрит на VPS):

```
budget.example.com {
    reverse_proxy 127.0.0.1:8081
}
```

Вариант с nginx, если он уже стоит: `location / { proxy_pass ... }` плюс
`proxy_set_header X-Forwarded-Proto https`.

Вариант без домена — Cloudflare Tunnel: адрес выдаётся сразу, но добавляется
зависимость от чужого сервиса и ещё один демон на машине.

Выбор фиксируется в README при деплое; на код он не влияет.

## 4. API

Всё под `/api`, ответы — JSON, ошибки — `{"error": "..."}` с осмысленным
кодом. Никакой вложенности ресурсов, никаких GraphQL.

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/me` | Кто я, кто партнёр |
| `GET` | `/api/categories` | 14 категорий |
| `GET` | `/api/transactions` | Список за период, фильтры `from`, `to`, `payer`, `category`, `kind` |
| `POST` | `/api/transactions` | Ручное добавление записи |
| `PATCH` | `/api/transactions/{id}` | Правка полей |
| `DELETE` | `/api/transactions/{id}` | Мягкое удаление |
| `GET` | `/api/report/month` | Четыре блока `plan.md` §10 |
| `GET` | `/api/report/daily` | Суммы по дням месяца — для графика |
| `GET` | `/api/usage` | Расход токенов, то же, что `/лимит` |
| `DELETE` | `/api/session` | Выход |

Отчёты считает существующий пакет `internal/report`. Дублировать его логику
в веб-слое нельзя: разойдутся цифры в боте и на сайте, и это обнаружится
не сразу.

### Права

Бюджет общий, поэтому **видеть можно всё**, включая записи партнёра. Менять
и удалять — только свои: то же правило, что у коллбэков бота (`plan.md` §9).
Чужая запись на попытку правки отдаёт 403, а не 404: скрывать её
существование бессмысленно, она и так видна в списке.

### Валидация правок

Сумма — единственное поле, которое веб позволяет менять, а бот нет. Значит,
проверять её надо здесь же, а не надеяться на `check` в базе:

1. `amount` — больше нуля, не длиннее `numeric(12,2)`.
2. `kind` ∈ `{expense, income, transfer}`, `beneficiary` ∈ `{payer, partner, both}`.
3. `kind='transfer'` → `beneficiary` форсируется в `partner`, категория
   обнуляется. Ровно правило `plan.md` §8, вызывается из общего места.
4. `spent_at` не дальше суток в будущем и не раньше 2020 года.
5. `description` обрезается до 64 символов.
6. `category_id` обязан существовать в `categories`.
7. Любая правка проставляет `updated_at = now()`.

Смена категории или бенефициара руками уезжает в `word_map` с
`source='manual'` — как и в боте, и с той же защитой от засорения словаря
описанием деградированной записи.

## 5. Фронтенд

React 18 + Vite + TypeScript. Сборка кладётся в `internal/web/dist` и
вкладывается в бинарь через `embed.FS`. Ни SSR, ни Next.js: страница
статическая, данные приходят из API.

Три экрана, между ними — hash-роутинг руками. Роутер как зависимость на три
экрана не нужен.

**Список.** Месяц переключается стрелками. Записи сгруппированы по дням,
строка — сумма, категория, кто платил, на кого. Свои записи кликабельны,
чужие открываются только на просмотр. Внизу — итог за месяц.

**Карточка.** Все поля из §4, кнопка удаления с подтверждением. Правка
суммы и даты — то, ради чего всё затевалось.

**Отчёт.** Четыре блока `plan.md` §10 плюс графики:

- кольцевая диаграмма по категориям;
- столбики по дням месяца (видно всплески);
- две полосы: кто платил и на кого ушло.

Графики — `recharts`. Раз npm уже в проекте, писать SVG руками ради трёх
диаграмм смысла нет.

Оформление своё, тёмная и светлая тема по `prefers-color-scheme`. Вёрстка
под телефон в первую очередь: открывать это будут с него.

## 6. Отказоустойчивость

- HTTP-сервер живёт в своей горутине. Паника в обработчике не должна ронять
  бота: `recover` в middleware, ошибка в лог, пользователю 500.
- Graceful shutdown: сначала `http.Server.Shutdown`, потом бот, потом пул
  БД. Порядок обратный запуску.
- Веб не мешает записи трат. Если база отвечает медленно, страдает страница,
  но не приём сообщений: у веба свои таймауты и свои соединения из пула.

## 7. Тесты

**Аутентификация** — самое важное, тесты на настоящей базе:

- токен входа срабатывает один раз, второй переход отказ;
- протухший токен (старше 5 минут) не работает;
- сессия чужого id, выпавшего из `ALLOWED_USER_IDS`, мертва;
- cookie без `Secure` не ставится, пока не задан `WEB_INSECURE_COOKIES`.

**API** — `httptest` поверх реальной базы, для каждого эндпоинта:

- без сессии → 401;
- чужая запись на `PATCH`/`DELETE` → 403 и запись не изменилась;
- своя → 200 и изменения в базе.

**Валидация** — сумма 0, отрицательная, `1e20`; дата в 2035 году; `kind`
из головы; `category_id`, которого нет; `transfer` с категорией.

**Отчёты** — те же данные, что в тестах `internal/report`, но через HTTP:
цифры на сайте обязаны совпасть с цифрами в `/месяц`.

Фронт тестами не покрывается — три экрана этого не стоят. Но
`npm run build` обязан быть зелёным, иначе фаза не закрыта.

## 8. Фазы

**Фаза 8.0 — каркас.** `WEB_ADDR`, `WEB_BASE_URL`, `http.Server`, роутинг на
`net/http`, отдача статики-заглушки из `embed.FS`, graceful shutdown,
`/api/health`. Проверка: бинарь поднимает сервер, `curl` отдаёт заглушку,
`SIGTERM` гасит всё в правильном порядке.

**Фаза 8.1 — вход.** Миграция 0004, `/вход` в боте, `/auth`, сессии,
middleware, `GET /api/me`, `DELETE /api/session`. Проверка: ссылка от бота
пускает, вторая попытка по той же ссылке отказывает, чужой id не проходит.

**Фаза 8.2 — чтение.** `GET /api/transactions`, `GET /api/categories`,
Vite-проект, экран списка. Проверка: с телефона видно траты за месяц, свои
и партнёра.

**Фаза 8.3 — правки.** `POST`, `PATCH`, `DELETE`, карточка записи, запись в
`word_map`. Проверка: опечатка в сумме исправляется, чужая запись не
поддаётся, удалённая пропадает из отчётов.

**Фаза 8.4 — отчёты и графики.** `GET /api/report/*`, экран отчёта, три
диаграммы. Проверка: цифры совпадают с `/месяц` в боте.

**Фаза 8.5 — эксплуатация.** Сборка фронта в Makefile, конфиг Caddy/nginx,
обновление systemd и README.

**Фаза 8.6 — необязательная.** Приём Telegram `initData` как альтернативы
cookie. Тогда тот же сервис открывается кнопкой внутри Telegram, без
отдельного кода фронта. Делать только если захочется — веб уже работает
и без этого.

## 9. Definition of Done

Открываю ссылку с телефона, вижу траты за месяц — свои и партнёра. Нахожу
запись, где сумма набрана с опечаткой, исправляю прямо в карточке, и цифра
в отчёте меняется. Смотрю на кольцевую диаграмму и понимаю, куда ушли
деньги. Партнёр делает то же со своими записями и не может испортить мои.
Посторонний по той же ссылке не видит ничего.

## 10. Чего в этой итерации быть не должно

- Регистрации, паролей, восстановления по почте, OAuth третьих сторон
- Публичного доступа хоть к чему-нибудь мимо whitelist
- SSR, Next.js, серверного рендера
- Любых обращений к LLM со стороны веба
- Экспорта в Excel, печати, PDF
- Долгов, мультивалютности, тегов, бюджетов по категориям
- Второй базы, очередей, кэшей в памяти между запросами
