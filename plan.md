# ТЗ: Telegram-бот учёта совместного бюджета

Документ — исполняемая спецификация. Реализовывать строго по фазам, снизу вверх. Не забегать вперёд, не добавлять функциональность, которой здесь нет.

Версия 4: разбор сообщений через LLM (Yandex AI Studio, модель Pro) с детерминированной валидацией сумм. Грант ежемесячный и с большим запасом — токены тратятся на качество разбора, а не экономятся.

---

## 0. Правила работы

- Язык: **Go 1.22+**. БД: **PostgreSQL 15+**.
- Никаких ORM. Только `pgx/v5` + `pgxpool` и голый SQL.
- HTTP-клиент к LLM — голый `net/http`. SDK `openai-go` не подходит: Яндекс использует схему авторизации `Api-Key`, а не `Bearer`.
- Никакого Docker, Kubernetes, микросервисов. Один бинарь + одна БД.
- Никакого веб-интерфейса в этой итерации.
- После каждой фазы: `go build ./...` и `go test ./...` зелёные, затем коммит. Не переходить к следующей фазе, пока текущая не зелёная.
- Все сообщения бота — на русском.
- Логирование через `log/slog`, текстовый формат.

### Definition of Done

Два человека пишут боту `600 лимонад` или `вчера взял в пятёрочке на 1200 и такси 400` — траты записываются с правильными суммами и категориями. Команда `/месяц` выдаёт четыре блока отчёта. Расход токенов виден по `/лимит`. Падение API или срабатывание защитного лимита не приводит к потере ни одной записи. Бинарь крутится на VPS под systemd, база бэкапится по крону.

## 1. Экономика гранта

Грант — ежемесячный, порядка 4000 ₽, обнуляется первого числа. При цене Lite 0.20 ₽ и Pro порядка 1–2 ₽ за 1000 токенов это от 2 до 20 миллионов токенов в месяц.

Реальная нагрузка: два человека, 30–40 сообщений в день, один вызов ≈ 700 токенов с few-shot примерами. Это ~840 тысяч токенов в месяц — меньше четверти гранта даже на Pro.

**Вывод, который определяет архитектуру: экономить токены не нужно.** Требования, продиктованные экономией, — короткий промпт без примеров, схема без пояснений, модель Lite — снимаются. Токены тратятся на качество разбора: модель Pro, развёрнутая схема, few-shot примеры.

Что остаётся и почему:

**Затравка словаря (§4) и кэш (§5)** — ради **скорости**, а не денег. Ответ из словаря приходит мгновенно, ответ от Pro — за секунду-две. Для короткого «600 лимонад» мгновенно ощутимо приятнее.

**Учёт токенов (§6)** — ради наблюдаемости. Нужно видеть фактический расход, чтобы решения принимались по цифрам, а не по ощущениям.

**Circuit breaker и жёсткий лимит (§7)** — ради защиты **от собственных багов**. Нормальное использование грант не выберет. А цикл в воркере, ретрай без backoff или случайно оставленный в проде отладочный прогон по всей истории — выберут, за ночь и молча. Лимит стоит в 4 раза выше реального потребления и в 10 раз ниже гранта: нормальную работу он не заденет, взбесившийся код остановит.

## 3. Схема БД

`migrations/0001_init.sql`:

```sql
-- +goose Up
create table users (
    id          bigint primary key,          -- telegram user id
    name        text   not null,
    created_at  timestamptz not null default now()
);

create table categories (
    id                   serial primary key,
    name                 text not null unique,
    default_beneficiary  text not null default 'both'
        check (default_beneficiary in ('payer','partner','both')),
    sort_order           int  not null default 100
);

-- общая затравка, одна на всех, заполняется миграцией
create table word_seed (
    word         text primary key,
    category_id  int  not null references categories(id),
    beneficiary  text check (beneficiary in ('payer','partner','both'))
);

-- личный кэш: слово → категория (и опционально бенефициар)
create table word_map (
    word         text   not null,
    user_id      bigint not null references users(id),
    category_id  int    not null references categories(id),
    beneficiary  text   check (beneficiary in ('payer','partner','both')),
    hits         int    not null default 1,
    source       text   not null default 'llm' check (source in ('llm','manual')),
    updated_at   timestamptz not null default now(),
    primary key (word, user_id)
);

create table transactions (
    id                   bigserial primary key,
    payer_id             bigint not null references users(id),
    beneficiary          text   not null check (beneficiary in ('payer','partner','both')),
    kind                 text   not null check (kind in ('expense','income','transfer')),
    amount               numeric(12,2) not null check (amount > 0),
    description          text   not null,
    category_id          int    references categories(id),
    raw_text             text   not null,
    needs_classification boolean not null default false,
    spent_at             timestamptz not null default now(),   -- дата траты
    created_at           timestamptz not null default now(),   -- дата записи
    deleted_at           timestamptz
);

create index tx_spent_idx  on transactions (spent_at) where deleted_at is null;
create index tx_payer_idx  on transactions (payer_id, spent_at) where deleted_at is null;
create index tx_needs_idx  on transactions (needs_classification) where needs_classification and deleted_at is null;

-- учёт расхода токенов
create table llm_usage (
    id                bigserial primary key,
    created_at        timestamptz not null default now(),
    model             text   not null,
    prompt_tokens     int    not null default 0,
    completion_tokens int    not null default 0,
    ok                boolean not null,
    error_kind        text                       -- timeout | quota | http | schema | other
);

create index llm_usage_month_idx on llm_usage (created_at);

-- +goose Down
drop table llm_usage;
drop table transactions;
drop table word_map;
drop table word_seed;
drop table categories;
drop table users;
```

`migrations/0002_seed_categories.sql` — ровно эти 14 категорий, не выдумывать свои. Тот же список уходит в enum JSON-схемы (§6), поэтому расхождений быть не должно.

| name | default_beneficiary |
|---|---|
| Продукты | both |
| Кафе и рестораны | both |
| Доставка еды | both |
| Транспорт | payer |
| Такси | payer |
| Жильё | both |
| Коммуналка | both |
| Связь и интернет | payer |
| Здоровье | payer |
| Одежда | payer |
| Хобби и развлечения | payer |
| Подарки | payer |
| Дом и быт | both |
| Прочее | payer |

### Ключевые смыслы полей

- `payer_id` — **кто заплатил**. Берётся из telebot автоматически, у пользователя не спрашивается никогда.
- `beneficiary` — **на кого потрачено**, относительно плательщика: `payer` (на себя), `partner` (на второго), `both` (на двоих).
- `kind='transfer'` — перевод денег между партнёрами. **Не расход.** Не попадает ни в один расходный отчёт. Иначе двойной учёт.
- `spent_at` vs `created_at` — модель понимает «вчера», «в пятницу». Отчёты строятся по `spent_at`.
- `needs_classification` — запись сохранена, но LLM не ответил. Добирается воркером.
- `raw_text` — исходное сообщение, хранить всегда.
- Удаление только мягкое. Все выборки содержат `deleted_at is null`.

## 5. Кэш-резолвер (быстрый путь, без API)

`internal/classify/cache.go`. Выполняется **до** обращения к API.

Условия срабатывания, все одновременно:
1. `tokens.Extract` вернул ровно одну сумму
2. в тексте нет слов-триггеров сложности: `вчера`, `позавчера`, `утром`, `днём`, `и`, `,`, `;`, перевод строки
3. каждое значимое слово описания найдено — сначала в `word_map` для этого `user_id`, при промахе в `word_seed`

Значимые слова: нижний регистр, длина ≥ 3, не из стоп-листа `для, что, как, там, тут, это, при, над, под, без, про, из-за, на, за`.

Приоритет при конфликте: `word_map` с `source='manual'` → `word_map` с `source='llm'` → `word_seed`. Внутри `word_map` при нескольких совпадениях — строка с максимальным `hits`.

Все три условия выполнены — транзакция собирается локально, API не вызывается, ответ приходит мгновенно. Иначе идём в LLM (§6).

В логах каждого сообщения фиксировать, сработал ли быстрый путь: это метрика скорости, а не экономии.

## 6. LLM-классификатор

`internal/classify/yandex.go`.

### Транспорт

```
POST https://ai.api.cloud.yandex.net/v1/chat/completions

Authorization: Api-Key <YANDEX_API_KEY>
OpenAI-Project: <YANDEX_FOLDER_ID>
Content-Type: application/json
x-data-logging-enabled: false
```

Заголовок `x-data-logging-enabled: false` обязателен — отключает сохранение запросов на стороне Яндекса. Через API едет история личных трат.

Поле `model` — URI вида `gpt://<YANDEX_FOLDER_ID>/<LLM_MODEL>`, собирается в коде из двух переменных окружения.

`temperature: 0`, `max_tokens: 500`, `stream: false`.

### Structured output

Яндекс поддерживает строгий `response_format` с JSON-схемой. Использовать обязательно.

```json
{
  "type": "json_schema",
  "json_schema": {
    "name": "transactions",
    "schema": {
      "type": "object",
      "properties": {
        "items": {
          "type": "array",
          "items": {
            "type": "object",
            "properties": {
              "amount":      {"type": "number", "description": "Сумма траты ровно так, как записана в сообщении"},
              "description": {"type": "string", "description": "Суть траты, 1-3 слова, без суммы"},
              "category":    {"type": "string", "description": "Категория траты", "enum": ["Продукты","Кафе и рестораны","Доставка еды","Транспорт","Такси","Жильё","Коммуналка","Связь и интернет","Здоровье","Одежда","Хобби и развлечения","Подарки","Дом и быт","Прочее"]},
              "beneficiary": {"type": "string", "description": "На кого потрачено", "enum": ["payer","partner","both"]},
              "kind":        {"type": "string", "description": "Тип операции", "enum": ["expense","income","transfer"]},
              "days_ago":    {"type": "integer", "description": "Сколько дней назад произошла трата, 0 = сегодня"}
            },
            "required": ["amount","description","category","beneficiary","kind","days_ago"]
          }
        }
      },
      "required": ["items"]
    }
  }
}
```

Список категорий в enum **генерировать в коде из таблицы `categories`**, а не хардкодить строкой. Иначе схема и БД разъедутся при первом же изменении.

Пояснения `description` внутри схемы обязательны — они заметно поднимают точность разбора. Экономить на них незачем.

### Системный промпт

Смысл, который должен быть передан (формулировку можно шлифовать, суть менять нельзя):

- Разбираешь короткие сообщения о личных тратах на русском. Пишут разговорно, с сокращениями и опечатками.
- Одно сообщение может содержать несколько трат — верни отдельными элементами.
- `amount` — число ровно так, как записано в сообщении. Не пересчитывай и не меняй разрядность. «к» означает тысячи.
- `description` — 1-3 слова по сути траты, без суммы и без указания, кому она.
- `beneficiary`: `payer` — на автора, `partner` — на его партнёра, `both` — на обоих. Если явно не сказано — реши по смыслу категории.
- `kind`: `transfer` — автор передал деньги партнёру, а не купил что-то. `income` — поступление. Иначе `expense`.
- `days_ago`: 0 если про день не сказано, 1 для «вчера», 2 для «позавчера».

**Few-shot примеры.** Включить в системный промпт не менее шести разобранных примеров — это главный рычаг точности на разговорном русском. Покрыть: простую трату, трату с явным маркером получателя, две траты в одном сообщении, трату со вчерашней датой, перевод партнёру, доход. Примеры писать в том же JSON, который ожидается на выходе.

Ориентир для агента (дополнить до шести и более):

```
"600 лимонад"
→ {"items":[{"amount":600,"description":"лимонад","category":"Продукты","beneficiary":"both","kind":"expense","days_ago":0}]}

"вчера взял в пятёрочке на 1200 и такси 400 домой"
→ {"items":[{"amount":1200,"description":"пятёрочка","category":"Продукты","beneficiary":"both","kind":"expense","days_ago":1},
            {"amount":400,"description":"такси","category":"Такси","beneficiary":"payer","kind":"expense","days_ago":1}]}

"скинул ей 5к"
→ {"items":[{"amount":5000,"description":"перевод","category":"Прочее","beneficiary":"partner","kind":"transfer","days_ago":0}]}
```

Пользовательское сообщение уходит как есть, без обёрток и без истории диалога.

### Режим вызова

- Быстрый путь сработал (§5) — API не вызывается.
- Иначе вызов синхронный, таймаут из `LLM_TIMEOUT` (по умолчанию 6 секунд). Один ретрай при 5xx и таймауте, backoff 500 мс. **При ошибке квоты ретрая нет** — повтор её не вылечит.
- Обе попытки провалились — транзакция сохраняется в деградированном виде (§8).

### Учёт токенов

Ответ API содержит объект `usage`. После **каждого** вызова, успешного или нет, писать строку в `llm_usage`: модель, `prompt_tokens`, `completion_tokens`, флаг успеха, вид ошибки. При ошибке токены пишутся нулями.

Без этой таблицы невозможно понять, куда уходит грант, и любые рассуждения об экономии становятся гаданием.

## 7. Circuit breaker и защитный лимит

`internal/classify/breaker.go` и `budget.go`.

Важно понимать назначение: **это защита от бага, а не от расхода.** Нормальное использование грант не выберет и близко. Опасность в другом — цикл в воркере, ретрай без backoff, случайный прогон переклассификации по всей истории. Такой код молча съедает месячный грант за ночь.

### Классификация ошибок

| Признак | `error_kind` | Реакция |
|---|---|---|
| HTTP 402, 429, либо тело содержит упоминание квоты/лимита | `quota` | breaker открывается на 30 минут |
| context deadline | `timeout` | один ретрай, затем деградация |
| HTTP 5xx | `http` | один ретрай, затем деградация |
| Ответ не проходит JSON-схему | `schema` | деградация без ретрая |

Ошибка `quota` ретраем не лечится — повтора для неё нет.

### Breaker

Три подряд ошибки вида `quota` или `http` — breaker открыт на `LLM_BREAKER_COOLDOWN`. Пока открыт, классификатор **не делает сетевых вызовов вообще**: и обработчик сообщений, и воркер добора сразу уходят в деградированный путь. По истечении — одна пробная попытка, успех закрывает breaker.

Это же защищает от спама в логи, когда API просто лежит.

### Защитный лимит

`LLM_MONTHLY_TOKEN_BUDGET` — потолок в токенах за календарный месяц. Считается суммой `prompt_tokens + completion_tokens` из `llm_usage` за `date_trunc('month', now())`.

- **80% потолка** — разовое уведомление владельцу бота (первый id из `ALLOWED_USER_IDS`). Повторно в этом месяце не слать. При нормальной работе это сообщение не должно приходить никогда; если пришло — где-то баг, идти смотреть `/лимит`.
- **100% потолка** — сетевые вызовы прекращаются до начала следующего месяца. Бот продолжает работать на кэше и затравке, непокрытое копится с `needs_classification`.
- **Новый месяц** — счётчик обнуляется сам по `date_trunc`, режим снимается автоматически. Отдельного сброса не нужно.

Значение выставляется в 3–4 раза выше ожидаемого расхода. При 30–40 сообщениях в день и ~700 токенах на вызов ожидаемое — около 840 тысяч токенов в месяц, потолок 2 000 000.

### Команда `/лимит`

За текущий месяц:
- израсходовано токенов, процент от потолка, оценка в рублях по цене модели
- число вызовов API, из них неуспешных, с разбивкой по `error_kind`
- доля сообщений, закрытых быстрым путём без API
- состояние breaker

## 8. Валидация ответа и деградация

`internal/classify/validate.go`. Выполняется всегда, даже при валидном по схеме ответе.

Для каждого элемента `items`:

1. **Сумма.** `item.amount` обязана присутствовать в множестве из `tokens.Extract(raw)`. Сравнение точное, по `decimal`. Не совпало — элемент отбрасывается, в лог `slog.Warn` с исходным текстом и обеими суммами.
2. **Сумма > 0.** Иначе отбрасывается.
3. **Категория** есть в таблице `categories`. Иначе → `Прочее`.
4. **`beneficiary`** ∈ `{payer, partner, both}`. Иначе → `payer`.
5. **`kind`** ∈ `{expense, income, transfer}`. Иначе → `expense`.
6. **`kind == 'transfer'`** → `beneficiary` форсируется в `partner`, категория обнуляется.
7. **`days_ago`** приводится в диапазон `[0, 30]`.
8. **Описание** пустое → из исходного текста, обрезанное до 64 символов.

### Деградированный путь

Срабатывает при: открытом breaker, исчерпанном месячном бюджете, отказе API после ретрая, пустом `items` после фильтрации.

Условие — `tokens.Extract` нашёл хотя бы одно число. Тогда:
- сумма — первая из найденных
- описание — весь текст без суммы, обрезанный
- категория `null`, `beneficiary` = `payer`, `kind` = `expense`
- `needs_classification = true`

Ответ пользователю: `✓ 600 ₽ · категория позже`.

Если чисел в сообщении нет вообще — ответить `Не вижу сумму. Например: 600 лимонад` и ничего не сохранять.

**Потеря записи из-за недоступности или исчерпания API недопустима ни при каких условиях.**

### Запись в кэш

После успешной классификации — для каждого значимого слова описания:

```sql
insert into word_map (word, user_id, category_id, beneficiary, source)
values ($1, $2, $3, $4, 'llm')
on conflict (word, user_id) do update
set category_id = case when word_map.source = 'manual' then word_map.category_id else excluded.category_id end,
    beneficiary = case when word_map.source = 'manual' then word_map.beneficiary else excluded.beneficiary end,
    hits        = word_map.hits + 1,
    updated_at  = now();
```

Ручная правка пользователя (`source='manual'`) приоритетнее ответа модели и не перезатирается.

## 9. Сценарии бота

### `/start`

- `user_id` не в `ALLOWED_USER_IDS` → «Бот приватный», выход. Другой авторизации нет и не нужно.
- Иначе upsert в `users`, приветствие с примерами формата.

### Свободный текст

1. `tokens.Extract`. Пусто → ответ про формат, выход.
2. Быстрый путь (§5) либо LLM (§6) → валидация (§8).
3. Вставка транзакций, каждый item — отдельная строка.
4. Ответ с инлайн-клавиатурой, по одному сообщению на транзакцию.

Формат:

```
✓ 1 200 ₽ · Доставка еды · 👥 на двоих
```

```
[ 👤 мне ] [ 🧍 ей ] [ 👥 нам ]
[ 🏷 категория ]     [ 🗑 удалить ]
```

Если `spent_at` не сегодня — в первой строке дата: `✓ 1 200 ₽ · Продукты · 👥 · вчера`.

Для `transfer`:

```
↔ Перевод 5 000 ₽
[ 🗑 удалить ]
```

### Коллбэки

- **Бенефициар** — update транзакции, upsert `word_map` с `source='manual'`, отредактировать исходное сообщение (не слать новое).
- **Категория** — заменить клавиатуру сеткой категорий по 2 в ряд, после выбора update + upsert с `source='manual'`, вернуть исходную клавиатуру.
- **Удалить** — `deleted_at = now()`, сообщение в `🗑 удалено`, клавиатуру убрать.

Все коллбэки проверяют, что `payer_id` транзакции равен нажавшему.

### Команды

| Команда | Действие |
|---|---|
| `/месяц` | Отчёт за текущий календарный месяц |
| `/месяц 6` | Отчёт за июнь текущего года |
| `/день` | Траты за сегодня, списком |
| `/лимит` | Расход токенов и состояние breaker (§7) |
| `/категории` | Список категорий |
| `/помощь` | Шпаргалка по формату |

Продублировать латиницей: `/month`, `/day`, `/usage`, `/categories`, `/help`.

## 10. Отчёт `/месяц`

Границы периода — в таймзоне `TZ`, в БД уходят как UTC. Фильтр по `spent_at`.

**Блок 1 — Итого.** Сумма всех `kind='expense'`.

**Блок 2 — По категориям.** `group by category_id`, сортировка по убыванию, `null` → «Без категории». Сумма и доля в процентах.

**Блок 3 — Кто платил.** `group by payer_id`.

**Блок 4 — На кого ушло.** SQL не усложнять: вытащить `(payer_id, beneficiary, amount)` и посчитать в Go:

```
spent_on(U) = Σ amount где beneficiary='payer'   и payer_id = U
            + Σ amount где beneficiary='partner' и payer_id ≠ U
            + Σ amount где beneficiary='both'  / 2
```

Пример вывода:

```
📊 Июль 2026

Всего: 68 400 ₽

По категориям
  Продукты          22 100 ₽   32%
  Жильё             18 000 ₽   26%
  Доставка еды       9 300 ₽   14%
  ...

Кто платил
  Илья              47 200 ₽
  Аня               21 200 ₽

На кого ушло
  Илья              31 500 ₽
  Аня               18 900 ₽
  Общее             18 000 ₽
```

`kind='transfer'` не участвует ни в одном блоке.

Взаимные долги **не считаем и не показываем.** Данных хватает, фича сознательно отложена.

## 11. Тесты

### `tokens.Extract`

| Вход | Ожидаемое |
|---|---|
| `600 лимонад` | [600] |
| `такси 450` | [450] |
| `1 200 доставка` | [1200] |
| `1200,50 продукты` | [1200.50] |
| `1200.50 продукты` | [1200.50] |
| `3к аренда` | [3000] |
| `1.5к бензин` | [1500] |
| `500р кофе` | [500] |
| `вчера пятёрочка 1200 и такси 400` | [1200, 400] |
| `кофе` | [] |
| `0 тест` | [0] |

### `validate`

С подставными ответами модели, без сети:

- сумма из ответа отсутствует в токенах (модель вернула 12000 при `1 200` в тексте) → элемент отброшен
- категория не из списка → `Прочее`
- `kind='transfer'` → `beneficiary` принудительно `partner`, категория `null`
- `days_ago = 999` → приведено к 30
- `items` пуст при непустых токенах → деградированный путь, `needs_classification = true`

### Кэш-резолвер

- все слова в `word_map` и одна сумма → API не вызывается (мок, счётчик вызовов = 0)
- слово есть только в `word_seed` → API не вызывается
- слово-триггер `и` в тексте → API вызывается, несмотря на попадание в кэш
- `source='manual'` не перезатирается ответом модели

### Breaker и бюджет

- три подряд ошибки `quota` → breaker открыт, следующий вызов не идёт в сеть
- бюджет исчерпан → сетевых вызовов нет, транзакция сохраняется с `needs_classification`
- `llm_usage` за прошлый месяц не учитывается в текущем счётчике

`.env.example`:


`config.Load()` падает на старте, если пуст любой из: `BOT_TOKEN`, `DATABASE_URL`, `ALLOWED_USER_IDS`, `YANDEX_API_KEY`, `YANDEX_FOLDER_ID`.

**Настройка перед первым запуском** (описать в README):

1. API-ключ уже есть — положить в `YANDEX_API_KEY`.
2. Взять `folder_id` того каталога, к которому привязан ключ, — положить в `YANDEX_FOLDER_ID`.
3. Проверить доступные модели: `GET {LLM_BASE_URL}/models` с теми же заголовками. Поправить `LLM_MODEL` под фактический идентификатор Pro-модели. Lite использовать не нужно — грант позволяет Pro, а качество разбора разговорного русского у него заметно выше.
4. `LLM_PRICE_PER_1K_RUB` выставить по актуальной странице тарифов — используется только для оценки в рублях в `/лимит`.
5. Прогнать `cmd/classify-test` на нескольких фразах и убедиться, что ключ живой, схема принимается и few-shot работает.

**Воркер добора.** Раз в 10 минут: если breaker закрыт и бюджет не исчерпан — выбрать до 20 транзакций с `needs_classification = true`, прогнать через классификатор, обновить, снять флаг. Если breaker открыт или бюджет исчерпан — тик пропускается целиком, без сетевых вызовов.

**Напоминание.** Крон на `REMINDER_AT`. Для каждого пользователя из whitelist: если сегодня нет ни одной транзакции — «Что сегодня тратил?». Есть — молчать. Бот, который пишет каждый вечер независимо от поведения, отправляется в mute за неделю.

**Makefile:** `build`, `run`, `test`, `migrate-up`, `migrate-down`, `lint`.

**systemd** — юнит `budget-bot.service`, `Restart=always`, `EnvironmentFile`, непривилегированный пользователь. В `deploy/`.

**Бэкап** — `deploy/backup.sh`: `pg_dump` в файл с датой, ротация 30 дней, крон раз в сутки. Не опция: полугодовая история трат восстановлению не подлежит.

## 13. Фазы

**Фаза 0 — скелет.** Каталоги, `config`, подключение к БД, миграции 0001–0003 (включая затравку словаря), `/start` с whitelist. Проверка: бот отвечает на `/start`, в `users` есть запись, в `word_seed` ~60 строк.

**Фаза 1 — токены.** Только `internal/tokens` и тесты. С ботом не связан. Проверка: все кейсы §11 зелёные.

**Фаза 2 — классификатор.** `classify.go`, `yandex.go`, `validate.go`, `cache.go`, `usage.go` и тесты. Плюс `cmd/classify-test`: принимает строку аргументом, печатает разобранный JSON и потраченные токены. Проверка: `go run ./cmd/classify-test "вчера пятёрочка 1200 и такси 400"` возвращает два корректных элемента с `days_ago=1`, в `llm_usage` появилась строка.

**Фаза 3 — breaker и защитный лимит.** `breaker.go`, `budget.go`, деградированный путь, тесты. Проверка: с заведомо неверным `YANDEX_API_KEY` бот всё равно сохраняет траты с `needs_classification`, в сеть не долбится, в логах нет спама.

**Фаза 4 — запись трат.** Репозитории, обработчик текста, клавиатуры, коллбэки, запись в кэш. Проверка: сообщение записывается; повторное то же слово резолвится без вызова API (видно по логам и по отсутствию новой строки в `llm_usage`).

**Фаза 5 — отчёты.** `/месяц`, `/день`, `/лимит`, `/категории`, `/помощь`. Проверка: четыре блока считаются верно на подготовленном наборе данных.

**Фаза 6 — эксплуатация.** Воркер добора, напоминание, Makefile, systemd, бэкап, README.

Дальше — **пауза на три недели реального использования.** Ничего не дописывать. Смотреть на `/лимит`: если расход больше 20% потолка, искать баг.

Следующее имеет смысл, только если бот пережил этот срок:

- **Фаза 7 — голосовой ввод через SpeechKit.** Тот же аккаунт Yandex Cloud, тот же грант. Голосовое сообщение → распознавание → существующий классификатор. Наговорить трату на ходу проще, чем напечатать, а весь разбор уже написан — это самая дешёвая по трудозатратам фича из оставшихся.
- **Фаза 8 — Telegram Mini App** с графиками.
- **Фаза 9 — переразбор истории.** `raw_text` хранится с первого дня: при смене промпта или модели можно прогнать всю историю заново и сравнить категории. Запускать только вручную, отдельной командой, с явным подтверждением — это единственное место, где легко упереться в защитный лимит.
- **Фаза 10 — импорт из пуш-уведомлений банка** через Android-приложение с `NotificationListenerService`.

## 14. Чего в этой итерации быть не должно

- Docker, docker-compose
- ORM, кодогенерация схемы
- Веб-сервер, HTTP-эндпоинты, вебхук телеграма
- Стриминг ответов LLM, история диалога, контекст предыдущих сообщений в промпте
- Автоматический переразбор истории по расписанию — только вручную (§13, фаза 9)
- Регистрация, пароли, JWT — whitelist из env закрывает вопрос полностью
- Расчёт и показ взаимных долгов
- Графики, экспорт в Excel, теги, повторяющиеся платежи, мультивалютность
